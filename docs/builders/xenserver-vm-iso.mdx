# XenServer ISO Builder

Type: `xenserver-vm-iso`

Artifact BuilderId: `packer.xenserver`

The `xenserver-vm-iso` builder starts from an operating-system ISO and creates a brand-new
virtual machine on a remote XenServer host or pool using the XenAPI. It boots the
installer, drives it to completion (typically unattended via an autoinstall/kickstart/
autounattend answer file), lets Packer provision the running guest, and exports the
finished machine as an artifact.

- XenCenter is not required — everything is driven over the XenAPI.
- It uses the official [XenServer Go SDK](https://github.com/xapi-project/xen-api).
- Tested against **XenServer 9**. Builds against earlier versions are unsupported and
  may not work.

## Examples

The examples below are complete and copy-paste runnable. They keep credentials out of
the template by reading them from Packer input variables (populate them with
`PKR_VAR_*` environment variables — see [Connection](#connection)).

### Ubuntu (autoinstall, from an ISO URL)

This example downloads the Ubuntu Server ISO, serves the
[autoinstall](https://canonical-subiquity.readthedocs-hosted.com/en/latest/reference/autoinstall.html)
`user-data`/`meta-data` over Packer's built-in HTTP server, and connects over SSH once
the install finishes.

```hcl
packer {
  required_plugins {
    xenserver = {
      source  = "github.com/xenserver/xenserver"
      version = ">= 0.9.1"
    }
  }
}

variable "xenserver_host" {
  type      = string
  sensitive = true
}
variable "xenserver_username" {
  type    = string
  default = "root"
}
variable "xenserver_password" {
  type      = string
  sensitive = true
}

source "xenserver-vm-iso" "ubuntu" {
  # --- Connection (lab pool with a self-signed cert) ---
  xenserver_host     = var.xenserver_host
  xenserver_username = var.xenserver_username
  xenserver_password = var.xenserver_password

  # Verify the pool certificate in production: drop this and set
  # ca_cert_path to the pool's PEM instead.
  insecure = true

  # --- Installation media (downloaded, verified, then uploaded to the VM SR) ---
  iso_url      = "https://releases.ubuntu.com/24.04/ubuntu-24.04.4-live-server-amd64.iso"
  iso_checksum = "sha256:e907d92eeec9df64163a7e454cbc8d7755e8ddc7ed42f99dbc80c40f1a138433"

  # --- VM hardware ---
  vm_name        = "packer-ubuntu-2404"
  vm_description = "Ubuntu 24.04 built by Packer"
  vcpus          = 2
  vm_memory_gb   = 4
  disk_size_gb   = 20
  firmware       = "uefi"
  network_names  = ["Pool-wide network associated with eth0"]
  clone_template = "Other install media"

  # --- Autoinstall over the built-in HTTP server (serves user-data + meta-data) ---
  http_directory = "http/ubuntu-2404"
  boot_wait      = "5s"

  # Sent once: the UEFI sweep only repeats boot_command = ["<spacebar>"], and repeating
  # this one would re-enter the kernel argument. See boot_key_groups.
  boot_command = [
    "<wait><esc><wait>",
    "e<wait>",
    "<down><down><down><end>",
    " autoinstall ds=nocloud-net;s=http://{{ .HTTPIP }}:{{ .HTTPPort }}/",
    "<wait><f10>",
  ]

  # --- Communicator ---
  communicator = "ssh"
  ssh_username = "ubuntu"
  ssh_password = "ubuntu"
  ssh_timeout  = "60m"

  # --- Output ---
  format           = "xva"
  output_directory = "output-ubuntu-2404"
  keep_vm          = "never"
}

build {
  sources = ["source.xenserver-vm-iso.ubuntu"]

  provisioner "shell" {
    inline = ["echo provisioned by packer"]
  }
}
```

`http/ubuntu-2404/` must contain a `meta-data` file (may be empty) and a `user-data`
autoinstall file. The `s=http://{{ .HTTPIP }}:{{ .HTTPPort }}/` fragment points the
installer at Packer's HTTP server; `.HTTPIP`/`.HTTPPort` are filled in at build time (see
[Boot Command](#boot-command)).

### Windows (autounattend, from an ISO already on an SR)

This example uses a Windows ISO that already lives on an ISO SR (referenced by name),
delivers `Autounattend.xml` on an EFI-safe CD via `cd_files`, and connects over WinRM.

```hcl
packer {
  required_plugins {
    xenserver = {
      source  = "github.com/xenserver/xenserver"
      version = ">= 0.9.1"
    }
  }
}

variable "xenserver_host" {
  type      = string
  sensitive = true
}
variable "xenserver_password" {
  type      = string
  sensitive = true
}
variable "winrm_password" {
  type      = string
  sensitive = true
}

source "xenserver-vm-iso" "windows" {
  # --- Connection ---
  xenserver_host     = var.xenserver_host
  xenserver_username = "root"
  xenserver_password = var.xenserver_password
  ca_cert_path       = "pool-ca.pem"

  # --- Installation media already staged on an ISO SR ---
  iso_name = "Win11.iso"
  iso_sr   = "ISO library"
  # No guest_tools_iso: XenServer 8 and later ship no guest-tools ISO.

  # --- VM hardware ---
  vm_name        = "packer-windows11"
  vcpus          = 4
  vm_memory_gb   = 8
  disk_size_gb   = 60
  firmware       = "uefi"
  secure_boot    = true
  vtpm           = true
  network_names  = ["Pool-wide network associated with eth0"]
  clone_template = "Windows 11"

  # --- Autounattend delivered on a CD (works under UEFI; a floppy does not) ---
  cd_files  = ["autounattend/Autounattend.xml"]
  boot_wait = "3s"

  # One key dismisses "Press any key to boot from CD". A UEFI iso build sweeps it
  # across the window on its own, so no boot_key_groups is needed here.
  boot_command = ["<spacebar>"]

  # --- Communicator: WinRM ---
  communicator   = "winrm"
  winrm_username = "Administrator"
  winrm_password = var.winrm_password
  winrm_use_ssl  = true
  winrm_insecure = true
  winrm_timeout  = "45m"

  # --- Output ---
  format           = "xva"
  output_directory = "output-windows11"
  keep_vm          = "never"
}

build {
  sources = ["source.xenserver-vm-iso.windows"]

  provisioner "powershell" {
    inline = ["Write-Host 'provisioned by packer'"]
  }
}
```

### ISO

The installation media is named exactly one of two ways — by URL, or by the name of an
ISO already on the ISO SR. Naming both, or neither, is rejected at validation time.

**By URL** — Packer downloads the ISO, verifies it against `iso_checksum`
(`iso_checksum = "none"` skips the check and only warns), and uploads it as a new VDI
on the VM SR (see [Storage](#storage-sr)); `iso_sr` plays no part. These options are the
SDK's own, so they behave exactly as they do in every other Packer builder:

@include 'packer-plugin-sdk/multistep/commonsteps/ISOConfig-required.mdx'

@include 'packer-plugin-sdk/multistep/commonsteps/ISOConfig-not-required.mdx'

**By name** — the ISO is already present on `iso_sr`, and nothing is downloaded:

- `iso_name` (string) - Name label of an ISO on the SR named by `iso_sr`. Mutually
  exclusive with `iso_url`/`iso_urls`. Nothing is downloaded, so `iso_checksum` and the
  other download options are rejected in this mode. The lookup is confined to `iso_sr`,
  so an ISO of the same name on another SR is passed over.

- `guest_tools_iso` (string) - Deprecated. The name of a guest tools ISO already
  present in an SR, attached to the VM during the build. Unset by default, and
  no tools ISO is attached when it is unset. XenServer 8 and later ship no such
  ISO — Linux guest tools are a `LinuxGuestTools-*.tar.gz` tarball and Windows
  guest tools an MSI — so this is only useful against XCP-ng or legacy pools,
  and it is slated for removal. Unlike `iso_name`, it is looked up pool-wide.

> **Upgrading:** `iso_checksum_type` no longer exists. Give the algorithm as a prefix on
> the checksum itself — `iso_checksum = "sha256:<hash>"` — or leave it off and let Packer
> infer it from the hash's length. In a URL build, `iso_checksum_type = "none"` becomes
> `iso_checksum = "none"`; in an `iso_name` build, drop the option instead — converting it
> is rejected, since a build that downloads nothing has nothing to checksum.

### Storage (SR)

- `vm_sr` (string) - Name label of the SR that holds the new VM's disk. Defaults to the
  **pool's default SR**. Must be unique. Every VDI the build creates goes here, so it has
  to be writable: the disk, the CD built from `cd_files`, and an ISO fetched from
  `iso_url`/`iso_urls`.

  The disk's VBD carries `other-config:owner`, so `xe vm-uninstall` — and deleting the VM
  in XenCenter — reclaims that VDI along with the VM. The CD and the uploaded ISO are
  attached as CD drives and deliberately left unowned, so removing the VM later never
  takes an ISO with it. The build destroys those two VDIs itself on the way out, but only
  when it destroys the VM: with `keep_vm` set to `always`, or to `on_success` on a build
  that succeeds, they are left on the SR — one copy per build.

- `iso_sr` (string) - Name label of the SR `iso_name` is looked up in. **Required with
  `iso_name`**, and read by nothing else — no build writes to it, so an ISO library that
  is read-only is fine. Must be unique.

### Hardware / VM

- `clone_template` (string, **Required**) - Name label of the XenServer template to clone
  as the VM's starting point. Naming the template that matches the guest OS (for example
  `Windows 11`) lets XenServer optimize the virtual hardware for it: the VM inherits the
  template's `firmware`, `secure_boot`, vTPM, `vcpus`, `cores_per_socket`, `vm_memory_gb`
  and `disk_size_gb` unless the build sets them. Two of those are not symmetric: `vtpm` can
  only add a vTPM, never take the template's away, and setting `vcpus` on its own drops the
  template's `cores_per_socket` to one core per socket when the inherited value does not
  divide the new count. Name `Other install media` — the generic template — to define the
  hardware entirely from the options below: it describes no guest OS, so it supplies none
  of those sizes and `vcpus`, `vm_memory_gb` and `disk_size_gb` all become **required**.

  Run `xe template-list params=name-label` on the pool, or look at the template list in
  XenCenter's New VM wizard, to see what is available; the name must match exactly one
  template. A VM or a snapshot sharing the name label is not a clash and is never cloned
  here: this builder installs onto a fresh disk, and `xenserver-vm-clone` is the builder
  that takes a VM or a snapshot.

- `vm_name` (string) - Name of the new VM (no file extension). Defaults to
  `packer-BUILDNAME-TIMESTAMP`, where TIMESTAMP is the time the build started, in Unix
  epoch seconds. The plugin substitutes both parts itself, so neither the VM's
  name-label nor the exported file name ever carries a literal `{{timestamp}}`.

- `vm_description` (string) - Description of the new VM. Defaults to empty.

- `vcpus` (integer) - Number of virtual CPUs. **Taken from `clone_template`** — the VM is
  cloned from it, and this builder writes the count only when you set it. It has no
  default, so it is **required** alongside `Other install media`, which supplies none.

- `cores_per_socket` (integer) - Cores per socket. XenServer divides `vcpus` by it to get
  the socket count, and a pair that does not produce a usable one fails to validate on
  either of the two counts XenCenter refuses one: it must divide `vcpus` exactly, and the
  sockets it gives must not exceed 16, the limit Xen imposes. **Taken from
  `clone_template`**, and never required: it is the one sizing option `Other install media`
  does not ask for, and a VM without it runs one core per socket. Set on its own it is
  ignored, with a warning, and the VM keeps `clone_template`'s topology. Setting `vcpus` on
  its own keeps that topology too while it still fits the new count, and otherwise replaces
  it with the fewest cores per socket that does fit — `1` up to 16 vCPUs, `2` at 32, and the
  whole count on one socket when nothing smaller divides it — and says so. The alternative
  is a VM that will not start.

- `vm_memory_gb` (integer) - Memory in **GB**, where a GB is 1024³ bytes (a GiB). It is
  written to all four of the VM's memory limits — static and dynamic, minimum and maximum —
  so the guest gets a fixed allocation with no ballooning range. **Taken from
  `clone_template`**, on the same terms as `vcpus`, with no default, and **required**
  alongside `Other install media`.

- `disk_size_gb` (integer) - System disk size in **GB**, where a GB is 1024³ bytes (a GiB).
  The builder installs onto a fresh empty disk it creates at this size — `clone_template`'s
  own disks are never attached — so no minimum is enforced and a size below the template's
  is fine. **Taken from `clone_template`** all the same: an OS template carries no disks
  but does carry the sizes it wants provisioned (`other_config:disks`, the same description
  `xe vm-install` reads), and a custom template, such as one this plugin built, carries a
  real disk on device 0 to measure instead. It has no default either, so it is **required**
  alongside `Other install media`, which has neither.

> A template sized for its guest OS therefore needs no sizing options at all — `vcpus = 4`
> alongside `clone_template = "Windows 11"` overrides the template, and leaving it out keeps
> what the template says.

> `Other install media` describes no guest OS and so answers none of those questions. Each
> of `vcpus`, `vm_memory_gb` and `disk_size_gb` left out alongside it fails `packer
> validate` by name, with `<option> must be specified with clone_template 'Other install
> media': that template describes no guest OS, so it supplies no <option> for the VM to
> inherit.` There are no built-in numbers behind them, so pick the guest OS's own: Windows
> 11 wants 2 vCPUs, 4 GB and 64 GB, Windows Server installs in 2 GB and 32 GB, and a Linux
> guest in far less. Memory is the one worth getting right — Windows Setup does not fail
> when it is short of it, it stalls, and the build then waits out `install_timeout` (3h20m)
> and reports a timeout that blames your answer file. A `vm_memory_gb` of 1 warns at
> validate time for that reason, whatever the `clone_template`; ignore the warning if the
> ISO installs something other than Windows.

> `vm_name = ""`, `vcpus = 0`, `cores_per_socket = 0`, `vm_memory_gb = 0` and
> `disk_size_gb = 0` are rejected at validation time, not read as "unset" and replaced by
> `clone_template`'s value. Omit the option to take the template's.

- `firmware` (string) - `bios` or `uefi`. **Defaults to `clone_template`'s firmware** — this
  builder clones its VM too, and writes the boot parameter only when you set it. The generic
  `Other install media` template carries no firmware, which XenServer boots as BIOS; an OS
  template such as `Windows 11` carries `uefi`, so naming the right `clone_template` is
  usually enough and `firmware` is the override for when it is not. The value is trimmed
  and lower-cased before anything reads it, so `UEFI` and ` uefi ` both mean `uefi`, for the
  boot mode checks below and for `secure_boot` and `vtpm` alike. Anything that is not `bios`
  or `uefi` after that is refused at validate time with `firmware must be one of 'bios',
  'uefi', got '<value>'`, rather than reaching `VM.start` and failing there. A value that is
  only whitespace is rejected too: empty means "keep the clone source's", and `" "` is not
  empty.

  Setting it **fails the build immediately**, before the ISO is downloaded, when
  `clone_template` is an HVM source XenCenter would not let you switch either (a PV source is
  not checked) — the same rule its
  New VM wizard uses to grey a boot mode out:

  - `firmware = "bios"` over a UEFI source whose boot mode is already settled, or one
    carrying a vTPM (`platform:vtpm = true`, which is how a `Windows 11` template is set up);
  - `firmware = "uefi"` over a BIOS source whose boot mode is already settled.

  "Already settled" means `last_boot_CPU_flags` is populated: XenServer writes it on a VM's
  first start and never clears it, and `VM.clone`, `VM.copy` and import carry it across. The
  stock install templates have never run, so this only bites on a source captured from a VM
  that has. The override would otherwise produce a VM the installer silently refuses to run
  on, failing only once `install_timeout` expired. A source with neither property can still
  be overridden — installing a plain UEFI template under BIOS is a legitimate thing to want.

  A VM that would boot BIOS with a vTPM attached **fails the build** just before it is
  started, as a backstop for a source the check above could not read. Set `firmware = "uefi"`,
  or pick a template without a vTPM.

- `secure_boot` (bool) - Ask for UEFI Secure Boot. **Omit it to keep whatever
  `clone_template` has**, the same as `firmware`; set it to `false` to turn Secure Boot off
  explicitly. `true` **requires `firmware = "uefi"`, which must be set explicitly** — the
  build fails validation otherwise, because validation runs before the pool is contacted and
  cannot see what the template's firmware is.

  `true` does not force Secure Boot on. It writes `platform:secureboot = "auto"`, which the
  build reports as `Set Secure boot to Auto`, and `VM.start` resolves that against the pool's
  UEFI certificates: on a pool holding none the VM starts with Secure Boot off, and the build
  still succeeds because the builder never reads the setting back.

- `vtpm` (bool) - Attach a virtual TPM. `true` **requires `firmware = "uefi"`, which must be
  set explicitly**, for the same reason (the build fails validation otherwise). Defaults to
  `false`.

  `false` means "add none", **not "have none"**: `VM.clone` copies the vTPM of whatever
  `clone_template` names, and this builder leaves an inherited one alone. To build without a
  vTPM, name a `clone_template` that has neither a vTPM nor `platform:vtpm = "true"`: that key
  is copied by the clone, and XenServer creates a fresh vTPM from it at start. (The clone
  builder's `vtpm` is a tri-state
  and can destroy an inherited vTPM; this one cannot.)

- `has_vendor_device` (bool) - Give the VM the emulated PCI device through which Windows
  offers the XenServer PV drivers on Windows Update. **Defaults to `true`.** A Windows
  guest needs it for a clean shutdown, reboot and suspend; a Linux guest is PV-native and
  ignores it. Unlike `firmware` and `secure_boot`, **omitting it does not keep the
  template's value**: a clone inherits the setting from `clone_template`, but the builder
  then applies this option on top, and left unset it resolves to `true`. So a VM cloned
  from the stock `Other install media` template, which has the device off, ends up with it
  on — a Windows build gets the device without your setting anything. Set
  it to `false` only if you specifically want the device absent — the builder writes the
  flag only when it differs from the template, so a template that is already correct is
  never touched.

- `vgpu_profile` (string) - vGPU profile name for accelerated graphics (see the
  [NVIDIA vGPU documentation](https://docs.nvidia.com/grid/latest/grid-vgpu-user-guide/index.html)).
  Defaults to none. The name is matched against the pool's vGPU type model names as a
  case-insensitive substring and the first match wins, in whatever order XAPI lists the
  types — `t4-2q` selects `GRID T4-2Q`, while `T4` takes whichever T4 type comes back
  first — so name enough of the profile to be unambiguous. If nothing matches, or if no
  GPU group has the matching type enabled, the build fails at the attach step rather than
  handing back a VM without the vGPU. Exactly one vGPU is attached, on device 0.

- `network_names` (array of strings) - Networks (by name label) to attach as VIFs, in
  order: the first entry is the VM's first interface, and so on. Each name must match
  exactly one network on the pool; a name of the form `Network N` that matches nothing is
  retried as the built-in `Pool-wide network associated with ethN`. Setting it
  **replaces** the networking the VM inherited from `clone_template`: the VIFs `VM.clone`
  copied are destroyed first, so the list is the VM's complete set of NICs, on devices
  `0..n-1` in the order written. If omitted, the VIFs `clone_template` supplied are kept
  as they are — and if it supplied none, as `Other install media` does, the VM gets a
  single VIF on the pool's management network so the guest can still reach Packer's HTTP
  server. An explicit empty list is rejected, as is an entry that names no network: omit
  the option instead.

- `vm_other_config` (map of string→string) - Key/value pairs written to the VM's XAPI
  `other-config` once the VM exists. They are merged into the `other-config` the VM
  inherited from `clone_template` rather than replacing it, so an inherited key survives
  unless your map names it. The two build-provenance keys are written last and win over an
  entry of the same name — see [Build Provenance](#build-provenance). Nothing checks the
  keys or the values. Defaults to empty.

### HTTP

Packer can serve a directory over HTTP so the installer can fetch answer files
(autoinstall/kickstart/preseed).

- `http_directory` (string) - Directory to serve. Defaults to empty (no HTTP server). The
  server's address/port are exposed to `boot_command` as `.HTTPIP`/`.HTTPPort`. The port
  is picked automatically from the range 8000-9000 and cannot be configured, so the guest
  has to be able to reach that whole range on the machine running Packer.

- `http_bind_address` (string) - Address the HTTP server binds to, and the address handed
  to the guest as `.HTTPIP`. Defaults to empty, meaning every interface — in which case
  `.HTTPIP` is derived from the route to `xenserver_host` (see below). `0.0.0.0` and `::`
  count as empty here: they bind every interface but name no address the guest can call back
  on, so `.HTTPIP` still comes from the route lookup. Set this when the
  machine running Packer reaches the guest on a different network from the one it reaches
  the pool on. It has to be an IP address — a hostname is rejected at validation time with
  `http_bind_address must be an IP address, got '<value>'`. Mutually exclusive with
  `http_interface`: setting both fails with
  `only one of http_bind_address or http_interface may be specified`.

- `http_interface` (string) - Name of a local network interface whose IPv4 address is
  handed to the guest as `.HTTPIP`. An alternative to `http_bind_address`; mutually
  exclusive with it.

### CD-ROM

- `cd_files` (array of strings) - Files placed on a CD attached at boot — most commonly
  `Autounattend.xml` for Windows. Each entry is a literal path: a file lands in the CD
  root, a directory is copied onto the CD under its own name. Wildcards are **not**
  expanded, and an entry that does not exist on disk is rejected before the build starts
  with `cd_files: '<path>' does not exist`. The ISO itself is built on the machine
  running Packer, which therefore needs one of `xorriso`, `mkisofs`, `hdiutil` or
  `oscdimg` on its `PATH`; nothing probes for those binaries at validate time, so a
  machine that has none of them fails part-way through the build, when the CD is created.
  The CD is always built with the volume label `cddata`, so cloud-init's NoCloud
  datasource — which looks for a filesystem labelled `cidata` — does not find a seed
  placed here unless the guest is pointed at the device explicitly. **Works under both
  BIOS and UEFI** (prefer this over a floppy for UEFI guests). The CD is uploaded to the
  VM SR. Defaults to none.

### Boot

- `boot_command` (array of strings) - Keys typed over VNC to start the installer (see
  [Boot Command](#boot-command)). If omitted, the installer is assumed to start on its
  own.

- `boot_wait` (string) - How long to wait after power-on before typing `boot_command`
  (for example `5s`, `1m30s`). Defaults to `5s`. `0s` is not "no wait" — it is
  indistinguishable from leaving the option out, so it also waits 5s; only a negative
  duration (`-1s`) skips the wait.

- `boot_key_groups` (integer) - How many times to repeat the whole `boot_command`
  sequence. Use it with `boot_key_group_interval` to catch a boot prompt that appears at
  an unpredictable offset — the UEFI "Press any key to boot from CD" window, for example,
  which is open for only about six seconds.

  **On a UEFI guest it defaults to 20 repetitions 1 s apart, but only when `boot_command`
  is a single `<spacebar>`** — a key that answers "press any key" without choosing
  anything. The window opens only once the firmware has worked through its boot entries
  and reached the DVD, which no fixed `boot_wait` can be aimed at, so the press is swept
  across it.

  Everything else defaults to 1 (send once): a BIOS guest, `xenserver-vm-clone` (whose
  guest boots no installer CD), and any other `boot_command`. Every repetition lands in
  whatever the first one started, so only a key that cannot act is repeated unasked —
  `["<down><enter>"]` picks a boot menu entry, and the repeats would move and commit
  selections in the installer it booted; a kernel command line typed at an isolinux or
  GRUB prompt would be entered again; and a `<wait>` is paid on every repetition, which
  stretches the sweep past the window it exists to cover. The build says which of the two
  it chose, and `boot_key_groups` with `boot_key_group_interval` sweeps anything you want
  swept.

  Set it explicitly to override either way. A value above 1 needs
  `boot_key_group_interval` with it. `0` means the same as leaving it out. A negative
  value is refused at validate time with `boot_key_groups must be at least 1, got N`.

- `boot_key_group_interval` (string) - How long to wait between successive `boot_command`
  repetitions, for example `"1s"`. No wait follows the last repetition.

  **Required when `boot_key_groups` is greater than 1.** Without it every repetition is
  sent at once and covers no more of the boot prompt than a single send would, so the pair
  is refused at validate time rather than running as a slower way of doing nothing.

  Defaults to 0, or to 1 s when `boot_key_groups` takes its UEFI default above — naming
  one of your own there replaces the 1 s and keeps the 20 repetitions.

### Communicator Configuration

Packer connects to the guest to run provisioners, using either SSH (Linux) or WinRM
(Windows), selected by `communicator` (`none` by default, then `ssh` or `winrm`). A build
that provisions the guest has to set `communicator` explicitly; the default logs in to
nothing and waits for the guest to power itself off.

> **Note:** each communicator asks only for its own credentials — `ssh_username` for
> `ssh`, `winrm_username` and `winrm_password` for `winrm`, and nothing at all for `none`.
> Earlier releases demanded an `ssh_username` on WinRM builds too, so templates written
> against them carry a throwaway one; it is ignored and can be removed.

With `communicator = "none"` Packer never logs in to the guest, so it cannot watch for an
address and cannot run provisioners. Such a build waits for the guest to power itself off
instead, for up to `install_timeout`, and fails if it does not. Make the unattended
installation shut the guest down when it finishes.

> **Note:** with `ssh` or `winrm`, the build waits for the guest to report an address
> whatever you set here, since that wait is also how it knows the install has finished. `ssh_host` and `winrm_host` then
> decide what it dials: unset, it dials the address the guest reported; set, it dials the
> one you named, which is what a guest reachable only through a NAT or a jump address needs.
> `ssh_port` and `winrm_port` are honoured as given.

#### Windows Remote Management (WinRM)

The guest must already be listening before Packer can connect. With `winrm_use_ssl = true`
that means an HTTPS listener on 5986, and a fresh Windows install has none. Create one from
the answer file, in `FirstLogonCommands`:

```powershell
Enable-PSRemoting -Force
$c = New-SelfSignedCertificate -DnsName $env:COMPUTERNAME -CertStoreLocation Cert:\LocalMachine\My
New-Item -Path WSMan:\localhost\Listener -Transport HTTPS -Address * -CertificateThumbPrint $c.Thumbprint -Force
Set-Item WSMan:\localhost\Service\Auth\Basic -Value $true
netsh advfirewall firewall add rule name='WinRM HTTPS 5986' dir=in action=allow protocol=TCP localport=5986
```

The certificate is self-signed, which is why the example sets `winrm_insecure = true`.

Do not open 5985 with `AllowUnencrypted` instead. The credentials would cross the network in
clear text, and Packer does not use that port while `winrm_use_ssl = true` — the build waits
for a listener that never answers.

### Output & Export

- `format` (string) - Export format: `xva` (default), `xva_compressed`, `vdi_raw`,
  `vdi_vhd`, or `none`. `none` exports no file and instead converts the finished VM into
  a template. That template is the output, so `none` defaults `keep_vm` to `on_success`
  and you need set nothing else. Naming `keep_vm = "never"` alongside it is still rejected
  at validation time: the template would be destroyed on the way out and the build would
  produce nothing at all.

  The template is converted from the VM the build installed onto, so it carries that
  installed disk, and the builder drops the two provisioning keys `VM.clone` copied off
  `clone_template` — `other_config:disks`, the description of the blank disks to create,
  and `other_config:postinstall`. Left in place they would describe a disk to create on
  device 0 on a template that already has one there: `xe vm-install` fails with
  `DEVICE_ALREADY_EXISTS`, and XenCenter's New VM wizard offers those phantom disks instead
  of the real one. The keys are only dropped on the output template; the VM's own
  `vm_other_config` is left alone.

  XVA exports are always gzip-compressed: the artifact is roughly 40-50% smaller and
  both import paths (the XAPI `/import` handler and `xe vm-import`) detect gzip
  transparently. `xva_compressed` is a deprecated alias — it is normalized to `xva`
  during validation and emits a warning, so existing templates keep working.

  `xva` writes a single file, `output_directory/<vm_name>.xva`. `vdi_raw` and `vdi_vhd`
  export the VM's disks one at a time instead, writing `output_directory/<vdi-uuid>.raw`
  or `output_directory/<vdi-uuid>.vhd` per disk, skipping CDs. `vdi_vhd` cannot export a
  disk larger than `max_vhd_size`, 2040 GiB: XAPI rejects it with `VDI_TOO_LARGE`. XAPI sends the `200` and
  the headers before it starts writing the body, so a failure part-way through the
  transfer arrives as a truncated file rather than as an error. Each exported file is
  therefore sanity-checked before the build is allowed to succeed: an export that wrote
  no file, wrote fewer than 512 bytes, or — for `xva` — does not start with a gzip or a
  tar header fails the build instead of being reported as a successful export. That
  catches an export that never started or died in its first bytes, but it is not an
  integrity check: nothing looks at the rest of the file, or at how many bytes were
  expected, so a transfer that fails later can still leave a short archive that passes.
  Check large artifacts yourself before relying on them.

- `output_directory` (string) - Directory the exported artifact is written to. Defaults to
  `output-BUILDNAME`. It is created if missing, and an existing empty one is used as it
  stands; if it holds anything at all the build stops before it starts and asks to be
  re-run with `packer build -force`, which deletes the directory and everything in it
  first. A cancelled or failed build deletes the directory on its way out, unless it is
  the one it refused to start in. `packer build -force` is not scoped to this directory:
  it also destroys any VM or template on the pool whose name-label is `vm_name`, and the
  disks they own.

- `keep_vm` (string) - When to keep the built VM: `never`, `always`, or `on_success`
  (keep it unless the build was cancelled or halted by a failing step). The default
  follows `format`: `on_success` when `format = "none"`, and `never` otherwise.
  `on_success` is judged on how the build ended, not on whether a file was written, so a
  `format = "none"` build keeps its template even though it exports nothing. Use `always`
  to hold on to the VM of a failed build for debugging.

  A kept VM does not take the `cd_files` disk with it: the build detaches that CD before
  the export, and the VDI behind it — name label `Packer-cd-disk` — is destroyed only when
  the VM is. Keeping the VM therefore leaves it on the VM SR, and nothing cleans it up
  later. Find and delete leftovers by hand:

  ```shell-session
  $ xe vdi-list name-label=Packer-cd-disk
  $ xe vdi-destroy uuid=<uuid>
  ```

- `create_snapshot` (bool) - Take a snapshot of the built VM once it has shut down and the
  install media has been detached, before it is converted to a template and exported.
  Defaults to `false`. The
  snapshot is treated as a requested artifact and is never cleaned up: it outlives the
  build even with `keep_vm = "never"`, which destroys the VM and its disks and leaves the
  snapshot and the snapshot's disks behind for you to delete.

- `snapshot_name` (string) - Name label for that snapshot. It is only read when
  `create_snapshot` is `true`: set on its own it is rejected, since it would take no
  snapshot, and left unset the snapshot is created with an empty name label.

### Advanced

- `install_timeout` (string) - How long to wait for the unattended installation to finish
  before failing. What the build waits for depends on the communicator: with `ssh` or
  `winrm` it waits for the VM to report an address to connect to, and with `none` it waits
  for the guest to power itself off. Defaults to `200m`.

- `shutdown_command` (string) - Command used to gracefully shut down the guest after
  provisioning. If omitted, the VM is shut down via the XenAPI. It runs inside the guest
  over the communicator, so it needs `ssh` or `winrm`: with `communicator = "none"` there
  is nothing to run it over, and it is rejected at validation time. The command and the
  wait for the VM to reach `Halted` share a single five-minute budget; if that runs out
  the VM is powered off hard.

The guest's IP address is discovered automatically: the builder takes whichever arrives
first, a callback to Packer's HTTP server or an address reported by the guest tools.

## Boot Command

`boot_command` is typed, character for character, over a **VNC** connection to the VM —
as if a human were at the keyboard — after `boot_wait` elapses. It is an array of strings
only for readability; the strings are typed in sequence.

Special keys are substituted:

- `<bs>` — Backspace
- `<del>` — Delete
- `<enter>` / `<return>` — Enter/Return
- `<esc>` — Escape
- `<tab>` — Tab
- `<f1>`–`<f12>` — Function keys
- `<up>` `<down>` `<left>` `<right>` — Arrow keys
- `<spacebar>` — Spacebar
- `<insert>` — Insert
- `<home>` `<end>` — Home / End
- `<pageUp>` `<pageDown>` — Page Up / Page Down
- `<wait>` — Pause one second before the next keys
- `<waitN>` — Pause for N seconds, for example `<wait5>` or `<wait45>`. Any Go duration
  also works: `<wait500ms>`, `<wait2m>`, `<wait1m30s>`

Anything that is not one of those tokens is typed as a character, which the VM's console
resolves as an X11 keysym. (A mistyped `<wait...>` is the exception: `packer validate`
rejects it rather than typing it in.) Keep boot commands to Latin-1 text (U+0020–U+007E
and U+00A0–U+00FF), the range that maps one-to-one onto keysyms: a character outside it
either has no keysym the console can map, and is dropped without a word in the log, or
lands in the X11 function and cursor key block at 0xFF00 — U+FF0D, a fullwidth hyphen, is
the keysym for Return. A literal newline or tab is typed like any other character and
reaches the guest as nothing; use `<enter>` and `<tab>`.

Each keystroke takes about 250 ms, so a boot command is not a way to deliver an answer
file — a kilobyte of it would type for minutes. Serve the file with `http_directory` or
`cd_files` and have the boot command point the installer at it.

Each string is also treated as a configuration template, with these variables:

- `.Name` — the name of the VM being built: the value of `vm_name`, or its generated
  default when `vm_name` is not set.

- `.HTTPIP` and `.HTTPPort` — the IP and port of Packer's HTTP server (from
  `http_directory`). With no `http_directory`, no HTTP server is started and `.HTTPPort`
  renders as `0` — not as a blank.

  `.HTTPIP` is the address of the machine running Packer, as seen from the guest. It is
  taken from `http_bind_address` or `http_interface` when either is set; otherwise it is
  the local address the operating system would use to reach `xenserver_host`. No
  connection to the XenServer host is made to work this out, so **dom0 SSH does not need
  to be enabled** — which matters on XenServer 9, where it is off by default. See
  [Host SSH access](#host-ssh-access).

Boot sequences are OS- and version-specific; tune the keys and waits for your installer.

## Troubleshooting

- **No IP address / build hangs waiting for the guest** — the build waits for an address
  for up to `install_timeout`. An address arrives from one of two places: the guest tools
  report it through XAPI guest metrics, or the guest fetches a file from Packer's HTTP
  server. So check that the guest received a DHCP lease, and that either the tools are
  installed in the guest (leave `has_vendor_device` on so Windows can fetch them) or the
  guest can reach the HTTP server (`http_directory` set, firewall open). A guest that will
  do neither — an unattended install answered from `cd_files`, with no tools — can never
  satisfy the wait, and the build must set `communicator = "none"`.

- **A `communicator = "none"` build fails after `install_timeout`** — such a build has no
  login, so it ends when the guest powers itself off. Make the answer file shut the guest
  down at the end of the installation (for Windows, a `shutdown /s` at the end of the
  unattended pass), or raise `install_timeout`.

  While it waits, the build reports the VM's power state and how many times the guest's
  domain has started, every two minutes. The count rises each time the installation reboots
  the guest, so one that stops rising well short of `install_timeout` is worth confirming on
  the VM's console rather than waiting the timeout out. A guest stopped on an installer
  dialog looks exactly like a slow install until you look at it.

- **A Windows install stalls and the build fails after `install_timeout`** — before you
  raise the timeout or reread the answer file, check `vm_memory_gb`. Microsoft's documented
  installation minimum is 4 GB for Windows 11 and 2 GB for Windows Server; below it Setup
  does not stop with an error, it stops making progress, and the progress reports above are
  the only symptom the build gives. Set `keep_vm = "always"` to leave the VM behind and see
  where Setup got to. Nothing supplies a floor: the value is whatever the build set, or
  whatever `clone_template` carries when it set nothing.

- **`boot_command` seems to miss keystrokes** — increase `boot_wait` and add `<wait>`
  tokens; the installer needs time to reach an input prompt before keys are typed.

- **The installer cannot fetch its answer file, and `.HTTPIP` looks wrong** — on a
  multi-homed machine the address that reaches the pool is not always the address that
  reaches the guest. Pin the right one with `http_bind_address` (or name the interface
  with `http_interface`).

- **`shutdown_command requires a communicator: it runs inside the guest`** — the two are
  refused together at validation time, before anything is created: `shutdown_command` runs
  over SSH or WinRM, so it cannot be used with `communicator = "none"`. Drop it and shut
  the guest down from the unattended installation itself; the build waits for the VM to
  power off.

- **`The shutdown command used the whole 5m0s allowed for a graceful shutdown without the
  VM halting`** — the command and the wait for the VM to reach `Halted` share one
  five-minute budget, and it ran out. The build does not stop here: it warns
  `WARNING: Forcing hard shutdown of the VM...`, powers the VM off hard and carries on to
  the export, so the exported disks are crash-consistent rather than cleanly shut down.
  Use a command that returns promptly — `shutdown /s /t 0` on Windows — so the halt lands
  inside the budget.

- **`An ssh_username must be specified.` on a WinRM template** — the plugin build predates
  CA-430886, which stopped the builder demanding an `ssh_username` from every communicator
  but `none`. Upgrade the plugin, or keep the throwaway username in the template until you
  can.

- **`winrm_password must be specified when communicator = "winrm"`** — the WinRM communicator
  authenticates with a username and password and nothing else, so a build without one would
  install and only then fail to connect. Set `winrm_password`, or export
  `XENSERVER_WINRM_PASSWORD`; the SDK option table above still lists it as optional because
  that table comes from the SDK.

- **`ca_cert_path must be specified when insecure is false`** — the builder verifies the
  pool's certificate by default. Export it with
  `xe host-get-server-certificate host=<host-uuid> > pool-ca.pem` and point `ca_cert_path`
  (or `XENSERVER_CA_CERT_PATH`) at it, or set `insecure = true` for a lab pool.

- **`certificate signed by unknown authority`** — `ca_cert_path` does not contain the
  certificate of the host that answered. For a pool it must hold every host's certificate,
  not only the coordinator's: an export, an upload, or the VNC console can be served by
  whichever host the object currently lives on.

- **`certificate is valid for X, not Y`** — the pool was reached by a name or address its
  certificate does not cover. Use a name the certificate is issued for, or reissue the
  certificate.

- **The build fails against a pool member that is not the coordinator** — the builder
  connects to whatever host `xenserver_host` names and never checks that it is the
  coordinator, so pointing it at a supporter host fails with XAPI's own `HOST_IS_SLAVE`
  fault, which the plugin passes through untranslated. Point `xenserver_host` at the
  coordinator (master), and update it if the coordinator has moved after an HA failover.

- **`clone_template must be specified`** — the builder used to substitute `Other install
  media` when the option was absent, which let it decide the VM's virtual hardware, and on
  that template its sizing, without the build saying so. Name the template that matches the
  guest OS, or name `Other install media` to keep what the substitution used to give you.

- **`<option> must be specified with clone_template 'Other install media'`** — the generic
  template describes no guest OS, so it carries no vCPU count, no memory size and no disk
  size for the VM to inherit, and the builder no longer invents one. Set each option the
  message names — they are reported together, so one `packer validate` lists all that are
  missing — or name the template that matches the guest OS and let it answer. A build that
  used to run on this template unchanged got 2 vCPUs, 4 GB and 64 GB; those are Windows
  11's documented minimum, not a recommendation for whatever you are installing.

- **`clone_template` not found / not unique** — the value must match exactly one *template*
  name label on the pool. A VM or a snapshot sharing the name is not a clash and is never
  cloned here; two templates with the same name are, so rename one.

- **`clone_template 'X' names a VM, not a template`**, or the same for a snapshot. The name
  resolved, but to something this builder does not take: it installs onto a fresh disk from
  install media. `xenserver-vm-clone` is the builder that clones a VM or a snapshot.

- **WinRM never connects** — confirm the guest has WinRM enabled and listening (HTTPS on
  5986 when `winrm_use_ssl = true`), the firewall allows it, and
  `winrm_username`/`winrm_password` are correct. `winrm_insecure = true` skips certificate
  validation for self-signed WinRM listeners.

- **`vtpm can only be enabled with firmware = "uefi", which must be set explicitly.`** —
  naming a UEFI `clone_template` is not enough here: validation runs before the pool is
  contacted, so it cannot read the template's firmware. Set `firmware = "uefi"` as well
  (Secure Boot behaves the same way).

- **The installer boots to a UEFI shell.** On bootable install media this is usually the
  boot command, not the firmware: a Windows ISO asks you to press a key before it will
  boot, and a press that lands before that prompt appears is lost. A UEFI iso build sweeps
  the boot command across the window for this reason, but only when `boot_command` is
  exactly `["<spacebar>"]` — any other command is sent once, because a repeat of it would
  land in whatever the first one started. So check first what `boot_command` is: if it is
  not that one key, name `boot_key_groups` and `boot_key_group_interval` yourself, or
  respell the dismissal as `<spacebar>` and let the default sweep it. Widening both
  options covers a slower host.

- **A BIOS-only ISO will not start.** The VM keeps `clone_template`'s firmware unless
  `firmware` says otherwise, and an OS template such as `Windows 11` is UEFI. Set
  `firmware = "bios"` to override the template — but pair it with a `clone_template` that
  boots BIOS, since a template whose boot mode is already settled, or that declares a vTPM,
  rejects the override rather than producing a VM that cannot install.

- **`clone_template 'X' boots with UEFI and declares a vTPM`** — a template whose
  `platform:vtpm` is `true` is built for a guest that requires TPM 2.0, and XenServer
  implements the vTPM for UEFI guests only. Remove `firmware` to keep the template's own
  `uefi`, or pick a `clone_template` that boots BIOS. This builder's `vtpm = false` is not a
  way round it: it only declines to attach a vTPM of its own, and it leaves `platform:vtpm`
  alone, so the key comes across with the clone and XenServer creates a vTPM from it when
  the VM starts. Only the `xenserver-vm-clone` builder's `vtpm = false` takes that key off.
  This is the same combination XenCenter greys the BIOS boot mode out for.

- **`clone_template 'X' boots with UEFI and its boot mode is already settled`** — the
  source's disk was laid out for UEFI, so a BIOS VM has no firmware to load its boot files
  with. What is read is `last_boot_CPU_flags`: XenServer writes it on a VM's first start and
  never clears it, and `VM.clone`, `VM.copy` and import all carry it across — so a template
  captured from a VM that ran counts as settled even though the template itself was never
  started. Remove `firmware` to keep the source's `uefi`, or clone from a source that
  already boots BIOS.

- **`clone_template 'X' boots with BIOS and its boot mode is already settled`** — the same
  rule in the other direction: a source laid out for BIOS has no EFI system partition, so
  UEFI firmware drops to the UEFI shell. Remove `firmware` to keep the source's `bios`, or
  clone from a source that already boots UEFI.

- **`this VM has a vTPM and will boot with firmware "bios" ... NOT_IMPLEMENTED [Booting BIOS
  VM with VTPMs attached]`** — the same combination as the first entry above, caught at the
  VM rather than at the source. The pre-build check reads `platform:vtpm`, so a source that
  carries the vTPM as an object without that key reaches here instead. The message says
  where the firmware and the vTPM each came from. `vtpm = false` does not resolve it, for
  the reason given above.

- **`Unsupported argument: iso_checksum_type`** — the option is gone. Move the algorithm
  into `iso_checksum` as a prefix (`"sha256:<hash>"`), or drop it and let Packer infer it.

- **`only one of iso_name or iso_url/iso_urls may be specified`** — a template that sets
  both used to be accepted, with the URL silently ignored. Keep whichever one the build
  actually meant.

- **`iso_sr must be specified with iso_name`** — `iso_name` is looked up in that SR, so
  the build cannot find the install ISO without it. This used to fail mid-build instead.
  An `iso_url` build needs no `iso_sr`: the ISO it downloads is uploaded to the VM SR.

- **`SR_BACKEND_FAILURE_78 ... VDI Creation failed`** on an upload — the target SR is
  read-only. Uploads go to `vm_sr`, or to the pool default when it is unset; point it at a
  writable SR (an `lvm`, `ext` or `nfs` one) rather than an ISO library.

- **`iso_checksum ... only apply to iso_url/iso_urls`** — `iso_name` attaches an ISO that
  is already on the pool, so nothing is downloaded and the download options would be
  ignored. Remove them, or switch the build to `iso_url`.

- **`Couldn't find a VDI named '...' in SR '...'`** — the ISO is not on `iso_sr`. The
  lookup is scoped to that SR now, so an ISO of the same name on a different SR no longer
  satisfies it.

## Required Privileges (RBAC)

XenServer uses [role-based access control](https://docs.xenserver.com/en-us/xenserver/8/users.html).
The build creates and destroys VMs, uploads/attaches VDIs, manages VIFs, and exports the
artifact, so the account in `xenserver_username`/`xenserver_password` needs at least the
**Pool Operator** role. Use **Pool Admin** if the build must also manage host
certificates or storage repositories. `root` (Pool Admin) always suffices.

The build calls no host-level operation beyond that, whatever it is configured to do:
`boot_command` reaches the VM's console through the XenAPI, and `shutdown_command` runs
inside the guest over the communicator. Neither logs in to dom0, so neither needs the
privilege to enable host SSH — see [Host SSH access](#host-ssh-access).
