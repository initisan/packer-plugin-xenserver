#### Supplying guest credentials from the environment

The credentials Packer logs in to the *guest* with fall back to environment variables the
same way the pool connection options do, so a build file need contain no password at all:

| Option                 | Environment variable             |
| ---------------------- | -------------------------------- |
| `ssh_username`         | `XENSERVER_SSH_USERNAME`         |
| `ssh_password`         | `XENSERVER_SSH_PASSWORD`         |
| `ssh_private_key_file` | `XENSERVER_SSH_PRIVATE_KEY_FILE` |
| `winrm_username`       | `XENSERVER_WINRM_USERNAME`       |
| `winrm_password`       | `XENSERVER_WINRM_PASSWORD`       |

A value set in the template always wins; the environment is only consulted for options the
template leaves out, and setting a variable to the empty string counts as not setting it.
Each communicator reads only its own set, so an exported `XENSERVER_SSH_PASSWORD` has no
effect on a `winrm` build, and a `communicator = "none"` build reads neither.

The fallback is applied before the options are validated, so a credential that comes from
the environment satisfies the check that would otherwise demand it — an `ssh` build with
`XENSERVER_SSH_USERNAME` exported needs no `ssh_username` in the template, and a `winrm`
build with `XENSERVER_WINRM_PASSWORD` exported needs no `winrm_password`.

~> **Do not hardcode guest credentials.** A password in a `.pkr.hcl` or `.pkrvars.hcl`
file is committed with it. Supply it from the environment, or declare it as a Packer input
variable marked `sensitive = true`. The same choice between the two applies here as for the
`XENSERVER_*` connection variables described under Connection Configuration.

With nothing about the guest login in the template at all:

```shell-session
$ export XENSERVER_SSH_USERNAME=builder
$ export XENSERVER_SSH_PASSWORD=...
$ packer build .
```
